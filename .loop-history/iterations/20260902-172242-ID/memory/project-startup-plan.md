# 项目启动规划

> 本文件是 S1 项目讨论阶段的启动快照。它只记录项目启动时的初始规划，S2 项目确认后冻结；后续阶段只读，用于溯源。S2 之后的范围、资料、字段或页面变更，不回改本文件，必须写入 `docs/decisions.md` 或 `memory/change-log.md`。

## 文件规则

- 写入阶段：S1 项目讨论。
- 冻结时机：S2 项目确认完成时。
- 后续用途：只读溯源。
- 后续变更位置：`docs/decisions.md` / `memory/change-log.md`。
- 禁止事项：S2 后不得修改本文件来伪造启动时已确认的范围。

## 启动来源

- 项目起点：基于已交付的“智能外呼统一中台”静态原型进行增量迭代。
- 底座项目：当前目录内已完成的六平台统一工作台，其中大众通信现有方式为关联平台已有任务。
- 底座保留内容：导航、六平台页面、大众任务 UUID 关联、模型与账号配置、任务详情、手工导入、全局标注运行时。
- 底座重置为空内容：本轮 loop 记忆、验收、执行步骤、验证日志和标注准备产物按新迭代重建。
- 底座禁止修改内容：非大众通信平台的业务逻辑、统一状态映射、租户计费、报表及已验证的数据口径。

## 产品形态

- 面向类型：企业级智能外呼运营管理。
- 载体形态：无构建步骤的 HTML/CSS/JavaScript B 端演示原型。
- 主要使用角色：外呼运营人员、业务管理员、产品/研发/测试评审人员。

## 项目目的

- 实现目的：解决大众通信任务无待呼号码后自动完成、导致任务内待重呼号码不再触发的业务风险，为运营人员提供可选重呼方式与人工确认门禁。
- 评审对象：产品、业务运营、研发与测试团队。
- 需要验证的业务假设：通过“不重呼 / 定时重呼 / 任务重呼”分支、定时重呼的人工确认与重呼次数记录，可以清晰提示平台限制并支持最后一次呼叫的业务判断。
- 不属于本次验证目标：不实现大众定时重呼真实接口，不自动验证大众后台是否已配置，不开发真实任务调度服务。

## 项目范围

- 本期模块：系统管理-业务场景，外呼管理-外呼列表，大众通信通话业务判断相关 Mock。
- 本期页面：`sys-scene` 大众通信配置面板、`scene-list` 大众通信任务详情，以及对应功能说明页。
- 本期能力：是否需要重呼；选择定时重呼或任务重呼；定时重呼关联任务 ID、计划重呼次数、人工已配置确认；任务重呼风险知情；确认人与确认时间追溯；最后一次计划呼叫判断。
- 核心流程：关联大众任务 UUID → 选择是否重呼 → 选择重呼方式 → 完成对应人工确认 → 保存场景 → 任务详情只读追溯。

## 非本期范围

- 不做模块：非大众通信平台配置、计费、标签、租户与报表模块。
- 不做页面：不新增独立页面，不改造与本轮无关的页面。
- 不做能力：不调用平台缺失的定时重呼接口，不声称中台已自动校验人工配置，不自动创建重呼关联任务。

## UI 风格

- 视觉基调：现有白底、蓝色主操作、浅灰分区的 B 端管理台。
- 是否沿用底座设计：是，复用既有表单行、单选组、提示框、开关、抽屉详情和状态标签。
- 参考风格：当前 `sys-scene` 平台专属面板与 `scene-list` 任务详情样式。
- 禁用风格：不新增营销式 Hero、大面积渐变、非底座卡片看板或独立视觉体系。

- 页面职责：`sys-scene` 负责录入、校验与人工确认；`scene-list` 负责展示重呼方式、配置追溯和最后一次判断结果。

## 核心流程

- 用户入口：系统管理 → 业务场景 → 新建/编辑 → 大众通信。
- 主流程步骤：填写任务 UUID；选择是否重呼；如重呼则选择默认推荐的定时重呼或任务重呼；定时重呼填关联任务 ID 和计划重呼次数并确认已在大众后台完成配置；任务重呼需确认已知悉完成态风险；通过校验后保存。
- 关键状态：不重呼、定时重呼-尚未人工确认、定时重呼-已确认、任务重呼-已知悉风险，以及非最后一次/最后一次计划呼叫。
- 异常或空状态：定时重呼缺关联任务 ID、重呼次数不合法或未人工确认时阻止保存；任务重呼未确认风险时阻止保存；切换方式或修改任务 ID/次数后清空旧确认。

## 验收方向

- 本轮完成后应看到：大众通信配置面板具有清晰分支、推荐标识、平台限制说明、必填校验、风险确认和只读追溯；详情可展示当前呼叫轮次及是否最后一次。
- 必须可用页面：`sys-scene`、`scene-list`、`docs/interaction.html`。
- 必须跑通流程：不重呼保存；定时重呼完整配置保存；定时重呼缺失项阻断；任务重呼风险确认；方式或关键值变更后确认失效；任务详情展示。
- 标注策略：人工触发且本轮要求回写；先生成 S9 标注提示词与覆盖清单，再按用户明确要求更新 `annotations/annotations.js`并复验。

## 约束和风险

- 技术约束：静态原型、ES5 页面脚本、无真实定时重呼接口；真实系统需在服务端持久化确认日志与呼叫轮次。
- 资料风险：重呼变更来自 PM 确认，平台未提供接口资料；原型不得写成已实现自动校验。
- 字段风险：“计划重呼次数”明确不包含首次呼叫；最大呼叫轮次 = 计划重呼次数 + 1。
- 人工核对项：定时重呼的关联任务 ID、实际重呼次数与大众后台配置必须由操作人确认，中台仅记录确认结果而不代表平台校验成功。

## S2 前待确认问题

- 阻塞确认项：无。PM 已确认人工配置方案、重呼方式选择、定时重呼次数及末次呼叫判断目的，并明确要求修改原型、说明和标注。
- 可带默认假设继续的问题：定时重呼作为默认且推荐方式；计划重呼次数为大于等于 1 的整数，前端不虚构平台未确认的硬上限；确认人使用当前演示用户“管理员”，确认时间使用浏览器当前时间。
